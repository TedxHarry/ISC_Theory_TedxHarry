## Example conditions and assessment review

10482 is a hypothetical business employee number, not an ISC identity ID. employeeNumber, employeeId and workerNumber are hypothetical external field names selected by prepared mappings/comparisons, not mandatory connector fields. staff-a and finance-b show separate account usernames without adding a biography.

All three external accounts exist before loading. Initially ISC has not loaded them and has no employee identity for this person. Source/profile/matching configuration and all required valid identity information are prepared. Same-subject matching values are reliable, the intended identity match is unique when comparisons occur and there are no conflicting records or earlier wrong associations.

HR-first collection establishes the employee identity with HR account association, employee number 10482 and department Finance. Directory and finance collection then associate their records using configured field pairs. This is a selected explanatory order, not a universal scheduling algorithm. No external creation, rename, permission write or attribute update is requested in that trace.

The separate empty-value variation starts with an existing employee identity and a never-associated directory account. Empty employeeId fails that comparison only. The full configured/default behavior is explicitly supplied as finding no authoritative employee match before describing the account as uncorrelated. Existing or manually maintained links need separate current-state/history investigation. No blanket absence of all identity-shaped representations is claimed.

Two directory accounts illustrate account-specific status/access on one source. The missing-link situation distinguishes external absence, uncollected/out-of-scope account and missing/wrong association. The creation scenario introduces a genuinely absent new-application account rather than an unrecognized existing one.

Later HR Operations is collected and applied to the identity through the selected mapping/processing. Account Finance can remain intentionally or because delivery/observation differs. Expected attribute synchronization requires its own applicable mappings, supported write and existing correlated account. The trace does not guarantee native acceptance or automatic readback. It does not use synchronization to create a missing account.

The four worked questions preserve the original purposes and causal answers. The warehouse transfer supplies a contractor identity, already existing/collected native account and unresolved expected relationship. It requires actual matching/association evidence before authorized correction; subsequent access adequacy stays a separate question.
