## Explanation and full author read-through

The opening explains what Windows-side execution adds to an approved directory change. IQService/Integration Service, Windows service and API meanings precede the component discussion. The connector's requirements establish its actual path, including all AD provisioning and selected reads; Terminal Services is explained only to the depth needed for that distinction.

The tenant, Linux VA/VM/cluster, Windows service host and target AD/domain/domain controller have distinct jobs. A precise group-membership requirement establishes the existing associated recipient, supplied document permissions, selected source/cluster/members/listener, request/profile and supported automatic provisioning before tracing execution.

The four-account comparison is followed by causal explanation rather than left as a glossary. The registered Windows client seeks admission; the service logon runs the program with required local resource access; the configured source service account supplies the documented target-operation context; the recipient receives membership. Registration does not create the Windows account, and account existence does not register it. Documented reuse of a service logon user as client does not collapse the separate checks.

The normal operation completes before the certificate variation. The component map shows the stated group update and returned results, with VA cloud initiation and the two downstream connections explained nearby. It does not generalize every read, packet sequence or automatic verification.

TLS explanation separates trusted endpoint identity from registered-client authentication and target-object authority. Plain key-pair reasoning explains why a public certificate alone is insufficient without the matching usable private key. Chain trust, endpoint name, dates and required account key access retain their distinct roles. The additional RFC reference supports this background meaning without teaching a version-pinned IQService handshake.

The complete saved learner was read in three contiguous portions, including both diagrams, both tables, five supplied expiry observations, all six worked cases and the different-connector read transfer. The read-through simplified credential/authentication wording, explained certificate proof without unexplained cryptographic terminology, defined process/admitted/execution context/reconciliation/rollback/timeout locally, and distinguished frontend display from backend operation. The native-script explanation now explicitly separates before-request and after-result modification under the supported interface.

The certificate case states a separate run with no delivered membership, a basic configured read path that does not use the rejected IQService leg, and a supplied pre-execution rejection. Later reasoning does not turn that into a universal every-read path or timeout outcome. Repair, supported recovery and target verification remain separate.

Scripting and maintenance retain operation-specific dependencies: current ScriptExecutor disabled default, TLS/explicit enablement, actual script context, after-failure execution, configured UpdateService and the VA-delivered package path. Shared Windows service dependencies explain why another VA does not remove that failure point.

Two diagrams and two tables serve actual component, credential and evidence distinctions. Length and counts follow the topic, not quotas. This is simulated beginner-oriented author review, not an observed independent learner study. Actual learner validation remains pending separately from continued authorized writing.
