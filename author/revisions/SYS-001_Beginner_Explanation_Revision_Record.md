## Teaching changes

The opening establishes an employee with a working account and a confirmed missing invoice-reading permission. The permission boundary and expected result are concrete before ISC objects accumulate.

The account-to-identity relationship is developed through its purpose: collect the existing account, associate it with the right person and identify where an authorized change should go. Matching uses agreed, correct unique employee information under prepared configuration; no biography or decorative identifier is needed.

Entitlement, access request, approval, provisioning, target and fulfillment are introduced through the change they describe. The main configured request path is completed before write-failure recovery, evidence freshness, manual delivery and automatic-assignment variations.

Role and lifecycle mechanisms are distinguished from an individual request, then connected to continuing need and access review. Governance, administration and IGA receive their names after the underlying responsibilities have been explained.

One decision/delivery diagram fits this subject. The permission comparison and screen/evidence comparison are useful for different purposes. No count, word limit or common section layout was imposed. Four original question purposes and the support/export transfer remain.

## Example conditions and outcomes

The employee has an existing identity and one existing invoice account. Sign-in works. The account initially lacks both hypothetical Read invoices and Release payments permissions and cannot perform those actions. The application owner confirms their different meanings and the reading requirement's intended resource scope.

The identity population exists, selected matching fields identify the same worker, their values are correct, the intended match is unique and correlation is configured. Source and connector integration are not substitutes for the application.

Entitlement requests are enabled; Read invoices is requestable/visible for this self-request; the correct manager is available and configured as reviewer. Immediate access has no future start or separate activation. No other independent configuration requires this permission in the main case.

The connector supports the addition, provisioning is enabled and connectivity/operation privileges are sufficient for the successful path. The application accepts the add; current permission/action checks establish reading and denied payment release, with no other relevant permission or native-rule change.

In the separate failure variation, integration authorization permits reads but not the required add. The supplied rejection changes nothing; current account evidence confirms missing Read invoices. Under an approved privilege correction and supported recovery, later checks confirm this account's result. That is not a universal retry instruction or proof of population recovery.

Manual delivery, automatic role eligibility, lifecycle account action, continuing cross-department need and limited campaign scope are variations, not hidden stages of the main request. The manual route is explicitly supported and owned; file import itself cannot perform the application change.

No fictional company, named employee, arbitrary employee number, account key or object ID is introduced. No real tenant observation is claimed.
