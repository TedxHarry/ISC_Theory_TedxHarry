## Conditions and limits

- No tenant, source, identity, account, priority, profile, mapping, processing, authentication path, credential or external access operation was performed.
- Main scenario starts with four collected accounts correctly associated with one existing intended identity. Both authoritative accounts already belong to it. Shared workerRef W-24 or similar labels are not treated as an automatic merge.
- Employee HR/Employees and Contractor Register/Contractors are authoritative arrangements. Corporate Directory and expense application are non-authoritative account sources. The directory supplies supported email input and configured PTA, with one intended available account.
- The normal initial-establishment explanation separately supplies a valid personnel record, configured profile and available required values. It doesn't assert that a new identity can always be created before a cross-source required input exists.
- Normal relationship diagram isn't a private order, guaranteed schedule, unconditional creation/matching rule or universal replay of unchanged-account correlation.
- Shadow representation for unmatched data differs from the intended authoritative-profile-backed person. No private storage model, one-to-one shadow count or absolute no-representation claim is made.
- Authority is source responsibility, not trust/data-quality score or read/write capability level. Directory authority can be valid under deliberate design; HR branding isn't sufficient.
- Initial Contractors 10/Employees 20 selects Contractors for this same-identity overlap. Its department mapping reads Vendor Services; HR account can simultaneously hold Finance.
- Approved corrected Employees 10/Contractors 20 with appropriate supported processing is supplied as producing Employees/Finance on the same identity, while directory email stays person@corp.example. Underlying account associations and values are unchanged in that supplied result.
- Profile-order change is population configuration and may affect other mappings, authentication/lifecycle/role/access behaviour. The example isn't a migration runbook or guarantee of universal relationship preservation.
- A profile applies only where relevant authoritative account relationships exist. Priority isn't identity merger, a latest-source rule or automatic per-attribute fallback.
- Non-authoritative mapped email is a supported input, not an additional simultaneously applicable identity profile. Transforms/fallback and manager relationships have their own explicit logic/conditions.
- uid/email/lastname are required mapped populated identity values; uid uniqueness spans identities/profiles. Null/defined schema/usable record and correct/deliverable email are different requirements.
- Missing input plus a lower-priority address doesn't establish fallback. No invented email or fabricated value is prescribed to silence an exception.
- Credential checking through configured PTA doesn't move to HR when HR is authoritative. SSO requires its own arrangement; no SSO route, shared password or credential copy is added.
- Authoritative designation doesn't implement missing writes or grant target authority. Identity profile and access profile are different objects. Identity processing can initiate provisioning without proving downstream success.
- Retained authoritative account plus changed status isn't supplied account removal. An outage also isn't deletion evidence. Actual profile association and relevant lifecycle/processing behaviour must be inspected.
- Profile reassessment after authoritative-account removal is scoped to supported full/account-deletion conditions. Remaining authoritative accounts can support reassignment; no remaining origin has conditional deletion/hidden handling and dependencies.
- Profile/feed/identity changes don't prove target deprovisioning or session termination. Deleting a profile has its own source-authority/identity/association consequences and isn't an incident shortcut; source/account records and external accounts aren't automatically removed by that action.
- Preview and saved configuration are distinct from applied processing and target result. Needs Processing is the documented profile state requiring appropriate application, not evidence every identity or external account changed.
