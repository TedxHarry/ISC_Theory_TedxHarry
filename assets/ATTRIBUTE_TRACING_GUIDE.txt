ISC attribute tracing guide
Revision: 2.0
Documentation verification date: October 26, 2026

An account attribute belongs to a collected source account. An identity attribute belongs to ISC's representation of a person or another entity. An identity profile supplies mappings that select or calculate identity values. A source is the configured account-data collection; its connector provides supported integration behavior. Account correlation associates accounts with their intended identities.

These questions record input, calculation and output evidence. They are not a universal execution sequence or instructions to change a tenant.

Normalization converts information into an agreed representation. An explicit input comes from the calculation's definition rather than the interface's selected source and field. Data type describes text, number or another kind of value; cardinality describes one value or a list.

1. Name the identity and output. Record the identity reference, governing profile, identity attribute's technical name, expected value and actual value. A matching display name alone does not identify the person or field.
2. Identify the configured input. Record the source and account attribute, plus any calculation or explicit input that changes where the value comes from. Inspect the saved definition, not just a familiar label.
3. Establish the account selection. Record the eligible associated account or accounts, their identifiers and any filter, sorting or null-selection behavior. One source can contain more than one account for a person.
4. Inspect the represented input. Record the actual collected value, whether it is text or another type, whether it is one value or a list, and when it was observed. Compare live producer data separately if freshness is in question.
5. Work through the calculation. Show the selected input and each relevant conversion or decision. Distinguish approved normalization from an incorrect field, missing data or an unjustified fallback.
6. Check the proposed result. Compare Preview with the expected value for this identity and representative population variations. A successful sample does not prove coverage, persistence or target delivery.
7. Verify the applied identity value. Record the relevant processing evidence and the value now shown on the identity. Separate a saved mapping, completed processing and the observed result.
8. Follow the consumers when required. Identify any matching, lifecycle, role, synchronization or provisioning behavior that uses this value. Verify each required downstream outcome with its own evidence; a correct identity value does not prove a successful target change.

Worked supplied trace
Employees governs an existing identity established through HR-Production. Work Email (email) selects the correctly associated Directory-Production account directory-user, attribute mail, with collected input USER-W103@EXAMPLE.INVALID. This is the only eligible directory account in the main example and there is no explicit input override. ToLower (technical operation lower) produces user-w103@example.invalid; the applied identity output is independently confirmed. Directory mail stays uppercase; no synchronization write is configured. Addresses are illustrative, not real mailbox evidence.

Account and value selection
For the accountAttribute transform, inspect the specific source/account filter, sort and null-handling configuration. Its default created-ascending order and first-non-null selection are not universal defaults for every ISC feature. accountReturnFirstLink=true returns the first sorted account's value even if null. Filtering controls eligibility; removing a filter to obtain an old populated value changes the input requirement.

For the specific profile mapping-transform behavior documented for multi-valued attributes, first-value conversion doesn't establish business meaning. With ["blr", "hyd"] and the supplied first-item uppercase behavior, BLR is a calculation result, not proof of primary location. Check the actual supported operation and required value shape.

Downstream checks
Identity processing evaluates identity information and applicable access requirements. A role can use identity values as criteria, and a lifecycle state can drive configured access. Attribute synchronization can send selected values to existing correlated accounts through provisioning, which performs supported external changes.

Preview shows proposed output for available data. Saved configuration, completed processing, observed identity value and target outcome are separate evidence. Applying a shared mapping can affect other identities and consumers.

Missing means a field wasn't supplied; null represents no value; an empty string has zero characters, while a space is a character. A list isn't one text value. Preserve identifier formats such as "0042" where required; converting to number 42 can lose meaning.

Required uid/email/lastname need non-null mapped values, and uid must be unique across profiles. A populated email isn't format, mailbox or delivery proof. Record unavailable evidence or approved input-design questions rather than substituting an arbitrary fallback.
